# Rules for working in notes/

> This file is a rule scoped with `paths:` to everything under `notes/` (the L2 description layer).
> It has the same shape as `.claude/rules/definitions-touch.md` (which targets the L1 machine layer),
> but its subject and the substance of its discipline differ.
> Its trigger conditions carry the same limitations as definitions-touch.md — it fires on Read, Edit is
> covered indirectly via the Read that precedes it, and a brand-new Write does not fire it, a known
> limitation (anthropics/claude-code#23478).
> `notes/` does not have as strict a write-path guarantee layer (PreToolUse hook) as definitions-touch.md.
> See section 0 for why.

## 0. Where this sits

`notes/` is this template's **L2 description layer** (see
`docs/decisions/2026-07-03-obsidian-context-stock.md`). It is a separate layer from `definitions/`
(L1, the declarative SSOT), accumulating stories, observations and procedures as Markdown with frontmatter.

- Unlike L1, `notes/` adopts Obsidian-compatible conventions, and the owner themselves is among those who
  write to it (limited to `notes/inbox/`). For that reason there is no guarantee layer as rigid as the hooks in
  definitions-touch.md. Instead, PII risk is absorbed by the "three nets" of RFC §4 (the owner principle,
  the secret-scan CI, and `/ingest-context`'s quarantine).
- Wanting to fix something in `notes/` does not change the structure of `definitions/` itself. Conversely,
  if you notice structural information (a new client, a KPI change, etc.), suspect the `definitions/` side
  rather than `notes/` (see definitions-touch.md).

## 1. Check before you touch anything (5 seconds)

Before calling Edit / Write, confirm:

1. ✅ Does the frontmatter satisfy the shared schema (section 2)?
2. ✅ Is the destination shelf appropriate for your role (section 3 — for the owner, `inbox/` only)?
3. ✅ Are you about to embed real names, real amounts or credentials directly (section 4)?
4. ✅ Are you violating the notation conventions for wikilinks, embeds and so on (section 5)?

## 2. Shared frontmatter schema (mandatory)

Every L2 note (under `notes/` as well as `docs/decisions/` and `docs/retros/`) carries the following keys.
See RFC §3 for details and the required keys per type.

```yaml
---
type: company-note | market | client-note | sop | inbox | decision | retro | digest
status: draft | active | superseded
created: 2026-07-03 # absolute dates only (the same principle as definitions-touch.md §2)
updated: 2026-07-03
tags: []
---
```

- `digest` (generated by `.claude/commands/digest.md`) is an aggregation result, not the SSOT.
  A note at the top of the body stating "This file is an aggregation result, not the SSOT" is mandatory.

- `notes/inbox/` is an exception. Because it is a shelf the owner writes to freely, frontmatter is not enforced.
  Frontmatter is applied when promoting to a shelf (`company/` `market/` `clients/` `sops/`)
  (`/ingest-context` or `/stock-note` does this for you).
- Existing files (created before this schema was introduced) are not retroactively bulk-edited.

## 3. Write conventions (who may write where)

The division of roles from RFC §4 applies as-is.

| Actor | May write to | Must not write to |
|---|---|---|
| Owner | `notes/inbox/` (free-form), typo fixes in existing L2 notes | Placing new files directly into `notes/company\|market\|clients\|sops/` |
| Agent | All shelves (following these conventions) | — |

- Promotion from inbox to a shelf goes via `/ingest-context` (inbox mode) or `/stock-note`.
  Do not place new files directly onto a shelf.
- `notes/inbox/` is tracked by git (do not gitignore it). Being readable by the agent in the next session and
  leaving a history are both essential as the starting point of the funnel.

## 4. Handling PII and secrets

Like `definitions/`, `notes/` is a folder that is expected to be **committed to git**.
Never write real names, real amounts or credentials anywhere, including `notes/inbox/`.

- Credentials -> `secrets/` (gitignored)
- Customers' real names and contact details -> reference by id (slug) and manage the real data separately
- Real contract amounts -> a range or an order of magnitude is acceptable

If you're unsure, re-read `.claude/rules/hitl-gate.md`. There is no mechanical block as rigid as
definitions-touch.md; instead this is absorbed in three stages: (a) it being the owner's own memo,
(b) the CI secret-scan, and (c) `/ingest-context`'s quarantine (RFC §4).

## 5. Link and notation conventions

- Wikilinks (`[[...]]`) only within `notes/` and only where they resolve uniquely. A root-relative full path is preferred
- References from L2 to L1 go through frontmatter ids (`entities:` / `client:` / `team_id:`). Do not point at
  YAML in `definitions/` with a wikilink in the body
- Embeds `![[...]]`, block refs `^xxx`, and Dataview / Bases query blocks are forbidden (app-dependent + fake-green risk)
- Callouts (`> [!note]`) are allowed

## 6. Relationship to the Scope Contract

Changes in `notes/` need less care than in `definitions/`, but avoid the following:

- Bulk rewrites spanning multiple notes ("while I'm here, let me make all the frontmatter consistent" amounts to
  retroactively editing existing files, which is against the principle in section 2)
- Copying inbox content onto a shelf as-is without quarantining it
