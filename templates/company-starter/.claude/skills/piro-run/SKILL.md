# piro-run - subagent-driven execution of a Kiro spec

piro's executor. Reads the 3 files in `.kiro/specs/<slug>/` (requirements.md / design.md / tasks.md),
has a fresh subagent implement the tasks in tasks.md one at a time, puts each through a review for spec
conformance and quality, and marks passing tasks `[x]` before moving on.

The Kiro-spec adaptation of superpowers:subagent-driven-development. Generating and changing specs is piro's own job
(this skill does not rewrite specs. The one exception is the checkboxes in tasks.md).

## Prerequisites

- The 3 files in `.kiro/specs/<slug>/` must be present in the target project
- Run on a git working branch. **Running directly on main/master is forbidden** (unless the user explicitly agrees).
  If there are uncommitted changes, stash them first

## Flow

### 0. Reading the spec and planning execution

1. If no slug is given, list what's under `.kiro/specs/` and confirm
2. Read requirements.md / design.md / tasks.md
3. Check the state of tasks.md:
   - `[x]` is complete. **Never re-run it** (the checkboxes in tasks.md are the source of truth for progress)
   - `[ ]` is what you execute, in the order written
   - `[ ]*` (optional) is also executed by default. Skip it only when the user says something like "skip the tests",
     leave it as `[ ]`, and state it plainly in the completion report
4. If there are contradictions between tasks, or a `_Requirements:_` reference that doesn't exist in requirements.md,
   raise them with the user once, all together, before execution (don't interrupt task by task)

### 1. The task execution loop (sequential. Parallel is forbidden)

For each leaf task (N.M):

1. **Assemble a brief**: write `task-N-M-brief.md` in the scratchpad. It contains
   (a) the full text of that task from tasks.md (including implementation notes),
   (b) the EARS requirements referenced by `_Requirements:_`, transcribed **verbatim** from requirements.md,
   (c) the relevant sections of design.md (components / data model / error handling).
   Don't make the subagent read all 3 spec files. The brief is the single source of requirements
2. **Dispatch the implementation subagent**: use [reference/implementer-prompt.md](reference/implementer-prompt.md).
   Record `git rev-parse HEAD` as BASE before dispatching
3. **Review**: once the implementer returns DONE, write `git diff BASE..HEAD` out to a diff file and dispatch a
   review subagent using [reference/task-reviewer-prompt.md](reference/task-reviewer-prompt.md)
   (on two axes: spec conformance and quality)
4. **Fix loop**: have a fix subagent address Critical/Important findings, then re-review.
   Don't move to the next task until it passes. Record Minor findings and carry them to the final review
5. **Once it passes**, update that line of tasks.md to `[x]` and commit
   (it can be a separate commit from the implementation. This is what makes the progress record Kiro-compatible).
   Mark a parent task (N) `[x]` once all of its subtasks are `[x]`

### 2. Checkpoint tasks

A `Checkpoint` task does not dispatch a subagent — the main thread directly runs the verification described
(build/test/behaviour check). If it fails, dispatch a fix subagent and only mark `[x]` once verification passes.

### 3. Wrapping up

1. After all tasks are complete, dispatch a final review subagent for the whole branch
   (hand it a diff package with BASE = the branch point, plus the accumulated list of Minor findings)
2. If there are findings, hand them all to a single fix subagent at once (don't split them up one per finding)
3. Completion report: tasks executed / optional tasks skipped / list of commits / remaining Minor findings

## Never do this

- **Do not create, edit or delete tasks.meta.json** (it belongs to Kiro)
- Do not re-run a task already marked `[x]`
- Do not rewrite anything other than the checkboxes in tasks.md (task wording, numbering, requirements.md, design.md).
  If you find a defect in the spec while implementing, report it to the user rather than fixing it yourself
  (fixing it is the job of piro's update mode)
- Do not dispatch implementation subagents in parallel (they collide in a single working tree.
  Wave parallelism is a feature of Kiro proper; this skill executes sequentially)
- Do not move to the next task while a review has not passed
- Do not re-dispatch under the same conditions when an implementer returned BLOCKED/NEEDS_CONTEXT
  (change one of: add context, move up a model tier, split the task, or escalate to the user)

## Model selection

Always state the model explicitly when dispatching (omitting it inherits the session's top-tier model):

- A task with concrete implementation notes touching 1-2 files -> a cheap model (haiku)
- A task needing multi-file integration or understanding of existing code -> standard (sonnet)
- The final review -> the highest-performing model available

## Resuming after an interruption

The source of truth for progress is the `[x]` marks in tasks.md and the git log. After a compaction or an
interruption, re-read tasks.md rather than relying on your own memory, and resume from the first `[ ]`.
