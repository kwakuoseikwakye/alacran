# The native app shell

Alacrán is a local Next.js server shown in a **native window**. It used to
start the server and then `open`/`xdg-open` the user's default browser; it no
longer touches a browser at all, except to hand off links that genuinely point
at the web.

Nothing about the server changed. `output: "standalone"` in `next.config.ts`
is already platform-agnostic, and the payload assembled around it
(`.next/standalone` + `.next/static` + `templates/`) is the same shape on
every platform, even though — since 2026-08-26 — mac and Linux assemble it
from two different repos (below). Only the **display step** is per-OS, and
now per-repo too.

## The three pieces

| Piece | What it does | Where |
| --- | --- | --- |
| Payload | The standalone Next server. Same shape everywhere. | `.next/standalone`, assembled by `scripts/package-linux.sh` (Linux) or the macOS desktop shell's `scripts/build-app-payload.sh` (mac) |
| Launcher | Finds a runtime, clears a stale port, starts the server, waits for it to answer, then runs the window. Owns the app's lifetime. | generated by `scripts/package-linux.sh` (Linux); the macOS shell's `electron/main.js` (mac) |
| Window | Shows the URL in a native window. | `scripts/webview-linux.py` (WebKitGTK, Linux); the macOS shell's Electron `BrowserWindow` (mac) |

**Linux is deliberately not Electron.** The OS ships a perfectly good webview
(WebKitGTK), so bundling ~200MB of Chromium would add weight, a second
update surface, and a rewrite of a packaging pipeline whose bug fixes are
individually documented in `CHANGELOG.md`. That reasoning held for mac too,
until 2026-08-26 — mac is now a deliberate, scoped exception to it, built as
an Electron app maintained separately from this repository, specifically
so this repo's own packaging pipeline (and Linux's Electron-free shape)
stays exactly as hardened as it was. Nothing below in this document describes mac's shell
anymore except where it's named explicitly.

## The window contract

Any platform's window shell must satisfy exactly this. Both existing shells
do — Linux's `webview-linux.py` process and the macOS shell's Electron
`BrowserWindow` alike — and a Windows one has to:

1. **The URL to show is known before the window opens.** Linux's window
   process takes it as `argv[1]`; Electron's main process, being the thing
   that already started the server, just knows it directly. No config file
   either way.
2. **The app's lifetime is the window's lifetime.** On Linux, the launcher
   `wait`s on the window process and its exit is what tells the launcher the
   user quit, which is what fires the trap that stops the server. Electron's
   `window-all-closed` handler does the equivalent directly. Closing the
   window quits the app either way.
3. **Keep local navigation inside the window, send everything else to the
   real browser.** `127.0.0.1`, `localhost` and `::1` load in-window;
   anything else opens externally and is cancelled. This is load-bearing, not
   polish: the app has `target="_blank"` links (release notes, changelog,
   tool docs), and every webview drops a new-window request unless the host
   handles it — so without this they silently do nothing at all.
4. **Retry a failed load rather than showing an error page.** The window is
   only ever shown once the server has already answered, so a later failure
   means the server died mid-session (usually an in-app update restarting
   it).

The launcher/main-process side has one matching rule: **if the server dies,
kill the window.** The browser build never needed it, because a browser tab
outlives its server. A native window must not sit there showing a dead page.

## Adding Windows

The app already *runs* on Windows; what it lacks is packaging. The code paths
that are platform-keyed degrade rather than break — `performUpdate` returns
"Automatic updates aren't available on this platform", and `restartAppImpl`'s
spawn failure is swallowed by its `on("error")` guard. So this is additive
work, not a migration.

What a Windows build needs:

- **`scripts/webview-windows.*`** — a WebView2 host satisfying the four rules
  above. WebView2 is preinstalled on Windows 11 and evergreen on Windows 10,
  so there is nothing to bundle; the runtime is the same class of OS-provided
  webview the other two shells use.
- **`scripts/package-windows.ps1`** — the same payload assembly
  `package-linux.sh` (in this repo) and `build-app-payload.sh` (in
  the macOS shell) both do (including the `templates/.` contents-copy
  and both payload assertions — see the comments in `package-linux.sh`, they
  encode a bug that shipped), plus a bundled `node.exe` (pinned and
  checksum-verified, as the other two platforms already do) and an installer.
- **A `win32` branch in `resolveDataDirFrom`** (`lib/data-dir.ts`). Windows
  currently falls through to the XDG path, which works but puts data in
  `%USERPROFILE%\.local\share\Alacrán` instead of `%APPDATA%`. Change this
  *before* the first Windows user exists, not after — it is a data migration
  afterwards.
- **A `win32` branch in `restartAppImpl`, `performUpdate`, and
  `canAutoUpdate`** (`lib/updates/`), if in-app updates are wanted. Shipping
  without them is fine: the download link is already the documented Windows
  fallback, the same way it already is for mac now.
- **Port clearing without `lsof`** — both launchers clear a stale prior
  instance off the port before starting. The Windows equivalent is
  `Get-NetTCPConnection -LocalPort`. Do not skip this; it is the fix for
  "installed the update but it still shows the old app" (v45).

Per the roadmap in `CLAUDE.md`, Windows is gated on the non-technical path
shipping and a real cohort being watched using it — this document is the
design being ready, not a decision to build it.
